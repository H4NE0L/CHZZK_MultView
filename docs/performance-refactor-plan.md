# 메모리 최적화·리팩토링 상세 설계

- 작성: 2026-10-29
- 상태: 1~5단계 사용자 테스트 완료. 마지막 6단계의 모듈·CSS·배포 정리를 구현했습니다. [6단계 안내](refactor-stage6.md)에 자동 검증 범위와 실제 Chrome 최종 확인 항목을 기록합니다. 실방송 장시간 측정·최종 사용자 검증·main 병합은 아직 완료되지 않았습니다.
- 기준 코드: `e399c5b`까지의 테스트 브랜치. 구현 시작 시 사용자 Chrome에서 확인한 커밋을 별도 기준점으로 고정합니다.
- 목표: 기능을 유지하며 자원 사용을 측정·개선하고, 변경 영향을 기능 단위로 제한합니다.
- 범위: 전용 멀티뷰와 치지직 페이지 모드, 팝업, 백그라운드, 콘텐츠 프레임, 녹화 결과/Worker.
- 버전: 다음 구조 개선 릴리스의 범위로 제안하며 실제 버전 번호는 릴리스 때 결정합니다.

## 1. 현재 구조에서 확인한 문제

| 위치 | 확인한 상태 | 변경 목적 |
| --- | --- | --- |
| `src/viewer/viewer.js` | 약 1,200줄에 UI 생성·상태·세션 저장·레이아웃·볼륨 UI·즐겨찾기 조회·메시지 분배가 공존 | 앱 조립과 기능 구현 분리 |
| `CZPlayers.create(...)` 등 | 공유 상태 getter와 다수의 상호 콜백으로 초기화 순서·갱신 순서를 연결 | 의존성과 상태 변경 경로 명시 |
| manifest / viewer HTML / site-viewer 파일 목록 | 같은 모듈의 순서와 누락을 여러 곳에서 관리 | import 기반 의존성과 빌드 진입점으로 통합 |
| 채팅 수집·표시 | DOM 선택·이름/역할/본문 해석·식별 이력·수집 정책·전송이 연결 | 외부 DOM 변경과 수집 정책을 각각 검사 |
| 이벤트·observer·타이머·객체 URL | 모듈마다 생성/정리 방식이 다름 | 생성한 기능이 자원을 명시적으로 해제 |
| 미디어 | 녹화 청크·결과 Blob·페이지 모드 전송·Worker 출력의 피크 메모리를 전체적으로 측정하지 않음 | 누적 사용량과 처리 중 복제 비용 확인 |
| JS 전역 `CZ*` | 실행 환경별 전역 선언과 스크립트 순서에 의존 | TS 모듈·타입 계약으로 단계적 교체 |

라인 수는 분리 후보를 찾는 참고값입니다. 짧게 압축된 함수도 많으므로 파일 길이만을 완료 기준으로 삼지 않습니다.

## 2. 유지할 동작과 진행 원칙

- 새 탭·새 창·치지직 페이지 모드와 최신 멀티뷰만 세션을 저장하는 규칙을 유지합니다.
- 타일 추가·제거·배치 변경 시 기존 iframe을 불필요하게 교체하지 않습니다.
- 타일 음량·전체 음량·메인만 듣기의 현재 격리 규칙을 보존합니다. 오디오 알고리즘 변경은 파일 이동과 별도 변경으로 다룹니다.
- 원본 치지직 채팅·사용자 메뉴·승부예측·외부 확장과의 상호작용을 보존합니다.
- 타임스탬프는 원본 작성 시각만 사용합니다. 원본 시각을 얻을 수 없는 문제는 DOM/데이터 어댑터의 별도 과제로 관리하고 관측 시각으로 대체하지 않습니다.
- 즐겨찾기·그룹·세션·설정 저장 키와 의미를 우선 유지합니다. 스키마 변경이 필요할 때만 버전과 이전 데이터 복원을 추가합니다.
- 기능 추가, 폴더 이동, 상태 로직 변경, TypeScript 전환을 한 변경에 섞지 않습니다.
- React/Vue 등 UI 런타임과 새 상태 관리 라이브러리는 이번 범위에 추가하지 않습니다.

## 3. 목표 구조

기존 실행 환경별 큰 폴더는 유지하고 내부를 역할별로 나눕니다. 모든 파일을 새 폴더로 옮기는 작업부터 시작하지 않습니다.

```text
src/
  shared/
    contracts/           # Channel, Session, Favorite, ChatMessage, 메시지 규약
    runtime/             # DisposableScope, 객체 URL 수명 관리
    storage/             # 세션·즐겨찾기·설정 저장 어댑터
    chzzk/               # API 응답 검증과 채널 정보 조회
  viewer/
    entry.ts             # 호스트 선택과 앱 시작
    app.ts               # 컨트롤러 조립·종료·최상위 액션 연결
    state/               # ViewerState, 세션 스냅샷·저장 조정
    layout/              # 그리드·상단바·잠금·패널 배치
    features/
      channels/          # 방송 목록 UI와 추가/제거 액션
      favorites/         # 즐겨찾기·팔로잉·그룹 UI와 갱신 조정
      audio/             # 음량 UI와 현재 음량 모델 연결
      chat/              # 원본 iframe 소유자·모아보기·설정 UI
      media/             # 캡처·갤러리·녹화 세션·결과 창
    recording/           # 결과 페이지와 export Worker 진입점
  content/
    entry.ts             # 검증된 프레임에서만 기능 조립
    player/              # 오디오·탐색·캡처/녹화 어댑터
    chat/
      dom-adapter.ts     # CHZZK DOM 선택자·작성 시각·이름/본문/역할 추출
      collector.ts       # observer·배치 전송·필터 적용
      history.ts         # 순수 식별·중복 정책과 상한
      layout.ts          # 원본 헤더·입력 UI 보정
    site-launcher.ts
  background/            # 탭/DNR·세션 소유자·쿠키·녹화 결과 서비스
  popup/                 # 팝업 진입점과 UI
  vendor/                # 버전 고정된 미디어 라이브러리·라이선스
```

폴더별 실제 이동은 해당 모듈을 작업하는 단계에서만 합니다. 사용처가 하나인 UI 보조 함수를 모두 shared로 옮기지 않습니다.

## 4. 상태와 의존성 설계

### 상태 분리

1. **저장 상태**: 채널 목록·배치·선택 방송·음량 설정·즐겨찾기·그룹·사용자 옵션. 검증된 스냅샷만 저장합니다.
2. **런타임 상태**: iframe 레지스트리·요청 중 작업·observer·녹화 세션·채팅 식별 이력. 세션 JSON에 넣지 않습니다.
3. **UI 상태**: 열린 설정·드래그·범위 조정·갤러리 선택 인덱스. 필요한 설정 외에는 지속 저장하지 않습니다.

외부 모듈이 viewer의 상태 객체를 직접 수정하지 않고 `addChannel`, `removeChannel`, `selectChannel`, `setTileVolume` 같은 명시적인 액션을 호출하게 합니다. 네트워크 조회와 DOM 갱신은 상태 저장 함수 안에서 실행하지 않습니다.

### 기능 간 연결

`ViewerApp`이 PlayerRegistry, AudioController, ChatController, FavoritesController, MediaController, LayoutController를 조립합니다. 각 기능은 최소 인터페이스만 받고 앱이 액션 결과와 상태 변경을 연결합니다.

예: 방송 제거는 앱이 녹화 중 여부를 확인한 뒤 플레이어 제거 → 해당 싱크/음량 런타임 상태 정리 → 선택 방송·채팅 조정 → 세션 저장을 조정합니다. 모듈이 다른 모듈의 DOM을 찾아 직접 수정하지 않습니다.

모든 기능이 사용하는 무제한 전역 이벤트 버스를 새로 만들지 않습니다. 메서드와 타입이 있는 제한된 이벤트로 연결하고, 테스트에서 액션 결과를 확인합니다.

### 외부 경계

- Chrome API·CHZZK API·DOM 추출·저장소를 어댑터로 분리합니다.
- 메시지는 `type`으로 구분하는 TS union으로 정의합니다. `uid`, 요청 ID, 성공/실패 응답을 명시합니다.
- TypeScript 도입 뒤에도 origin·sender·frame·UID 검사와 런타임 payload 검증을 유지합니다.
- 오래된 요청의 응답은 세대 번호/AbortSignal로 무시하거나 취소합니다. 이전 방송의 조회가 현재 UI나 즐겨찾기 이름을 덮어쓰지 않도록 합니다.

## 5. 자원 소유권과 메모리 정책

`createFeature()`는 기능 인터페이스와 `dispose()`를 반환합니다. `dispose()`는 두 번 호출해도 안전해야 하며 생성 중 오류가 나도 이미 만든 자원을 정리합니다.

`DisposableScope`는 하위 scope, 이벤트 리스너, observer, 타이머, AbortController, 객체 URL, Worker의 정리 함수를 등록합니다. 해제 후 끝나는 비동기 응답이 UI를 다시 만들지 않도록 합니다. 원본 플레이어에서 빌린 트랙과 자체 생성한 캔버스 트랙의 소유권을 구분합니다.

| 자원 | 소유자 | 해제/상한 |
| --- | --- | --- |
| 방송 iframe | PlayerRegistry | 방송 제거·멀티뷰 종료 |
| 원본 채팅 iframe | ChatController | 채팅 닫기·채널 전환·종료 |
| 수집 observer·시각 표시 observer | 해당 채팅 프레임 scope | 프레임 종료·기능 중단 |
| 모아보기 본문/DOM | ChatController | 최대 100개, 채널 변경·닫기·명시적 초기화 때 정리; 설정 변경은 제외 대상만 제거 |
| 수집 식별 이력 | ChatHistory | 최대 2,048개, 해시·ID·시각만 저장 |
| 스크린샷 Blob·미리보기 URL | ScreenshotGallery | 저장한 항목·닫은 갤러리에서 해제, 활성 이미지 위주로 디코딩 |
| 녹화 청크·자체 캔버스 트랙 | RecordingSession | 녹화 종료/실패 시 정리, 방송당 256MiB 유지 |
| 페이지 모드 전송 중 청크 | Background transfer | 완료·실패·탭 종료·만료 시 정리 |
| 녹화 결과 | 결과 저장소/탭 서비스 | 결과 창 닫기와 기존 만료 정책 |
| 내보내기 Worker·출력 ArrayBuffer | ExportJob | 완료·취소·창 닫기, transferable 사용 유지 |

현재 상한이 없는 스크린샷 전체와 동시 녹화의 합산 예산은 우선 측정합니다. 초기 검토 후보는 스크린샷 32장/128MiB, 동시 녹화 2개/합산 512MiB, 내보내기 동시 1개입니다. 이는 제안값이며 아직 구현하거나 확정한 기본값이 아닙니다. 예산을 적용할 때는 새 작업을 제한하거나 진행 중 작업을 정상 마감하며 저장하지 않은 결과를 몰래 삭제하지 않습니다.

이 예산은 확장이 소유한 데이터에 관한 것입니다. 동영상 디코더·GPU·치지직 원본 페이지를 포함한 전체 Chrome 메모리 상한을 뜻하지 않습니다.

## 6. TypeScript·빌드 설계

- 도구는 **TypeScript + esbuild**를 사용합니다. Chrome 119를 실행 대상의 하한으로 유지합니다.
- 신규/이동 모듈은 `.ts`와 `strict: true`를 적용합니다. 이행 기간에는 `allowJs`로 기존 JS를 연결하되 프로젝트 전체에 `checkJs`를 강제하지 않습니다.
- 진입점·공유 계약부터 타입을 붙입니다. 기존 복잡한 DOM 코드 전체를 처음부터 한꺼번에 strict로 바꾸지 않습니다.
- 외부 입력은 `unknown`에서 검증해 좁힙니다. 메시지·저장·API 경계에 광범위한 `any`나 `@ts-ignore`를 남기지 않습니다.
- background와 content script, 페이지 모드 주입 코드는 번들링한 **classic IIFE**로 출력합니다. content script의 native ESM 지원에 의존하지 않습니다.
- 녹화 내보내기 Worker는 별도 ESM 진입점으로 유지합니다. Mediabunny는 앱 초기 번들에 포함하지 않고 저장/변환 시에만 로드합니다.
- 같은 viewer 앱을 전용 페이지와 치지직 페이지 모드가 공통 사용하고 HostAdapter로 Chrome/페이지 모드 차이를 처리합니다. 앱 구현을 두 벌로 복사하지 않습니다.
- import 관계로 의존 순서를 관리하고 manifest·HTML·페이지 모드 주입 목록은 빌드 진입점 정의에서 생성/검증합니다.
- manifest 권한·CSP를 빌드 편의 때문에 넓히지 않습니다. eval·원격 코드·인라인 스크립트 없이 빌드합니다.

개발 명령의 목표:

```text
npm ci
npm run typecheck
npm test
npm run test:browser
npm run build          # dist/에 로드 가능한 확장 생성
npm run package        # dist/만 ZIP으로 묶음
```

도입 단계에서 package.json·lockfile·Node 버전 안내·빌드 스크립트를 추가합니다. 빌드 도구는 개발 의존성으로 두고 `dist`와 ZIP에 node_modules/TS 원문/개발 소스맵을 포함하지 않습니다. 개발 빌드는 로컬 소스맵을 사용할 수 있습니다. 기존 HTML·아이콘·Worker·vendor 라이선스와 앱 내부 URL 참조를 패키지 검사로 확인합니다.

| 3. 채팅 분리 | DOM 어댑터·순수 파서·수집 정책·이력·UI 분리, 선택자 fixture | 배지/역할/제외/중복/접기/원본 메뉴·타임스탬프 검사 통과 |
| 4. viewer 분리 | 상태 조정·즐겨찾기/팔로잉·레이아웃·음량 UI·방송 목록 추출 | app은 기능 조립/최상위 액션만 담당. 플레이어 유지·음량 격리·최신 창 저장 규칙 유지 |
| 5. 미디어 수명·피크 개선 | 캡처/녹화/전송/내보내기 scope와 예산, 지연 로드 검증 | 저장·취소·종료 뒤 불필요한 Blob/URL/Worker가 남지 않고 원본 트랙 보존 |
| 6. 정리와 릴리스 | 남은 전역 브리지/미사용 코드 제거, CSS 기능별 정리, dist 문서·패키징 | 양쪽 멀티뷰 모드의 실제 Chrome 점검과 장시간 측정 완료 |

각 단계는 여러 작은 커밋/PR로 나눕니다. 첫 단계부터 전체 폴더 이동이나 음량 알고리즘 재작성은 하지 않습니다. 배포 기준 코드에서 별도 refactor 브랜치를 만들고, 각 단계가 완료될 때 테스트 ZIP을 제공합니다. 현재 테스트 변경을 확인 없이 main으로 합치거나 릴리스 번호를 미리 올리지 않습니다.

## 8. 측정 시나리오와 판정

같은 Chrome 버전·장치·방송·화질을 사용하고 기존 버전과 비교합니다. 초기 로딩과 2분 정도 안정화한 뒤의 수치를 구분하고, 반복 시나리오는 가능하면 3회 측정합니다.

| 시나리오 | 확인할 값 |
| --- | --- |
| 0/1/4/9타일, 같은 화질 | 프로세스 메모리·JS 힙·CPU·GPU 관련 사용량·버퍼링 |
| 채팅 닫힘 / 원본만 / 모아보기 ON | 추가 연결 수·관찰자 처리량·수집 지연·메모리 차이 |
| 30분 시청·과거/실시간 스크롤 왕복 | DOM 개수·이력 상한·중복·누적 힙 증가 |
| 타일 추가/제거·채팅 열기/닫기 각 30회 | 해제 후 listener/observer/iframe/분리 DOM 잔류 |
| 스크린샷 반복 캡처·저장·닫기 | Blob·객체 URL·디코딩 이미지의 보유 수 |
| 저부하/원본 녹화·동시 녹화 | 인코더 부담·프레임 손실·청크/전송 피크 |
| WebM/MP4 구간 저장·변환·취소 | Worker 수·출력 버퍼·실제 트랙/파일 정합성 |
| 전용 페이지 / 치지직 페이지 모드 | 별도 원본 페이지와 외부 확장 영향 |

완료 기준:

- 기존 기능 검사와 실제 Chrome의 로그인·방송 재생·원본 채팅 조작이 통과해야 합니다.
- 앱 소유 자원 카운터는 기능 종료 시 허용된 기본 상태로 돌아와야 합니다. 다운로드 URL처럼 유예 해제가 필요한 것은 유예 후 확인합니다.
- 반복 종료 후 힙 스냅샷에서 앱의 detached DOM·폐기한 Worker/Blob에 대한 보유 경로가 지속 증가하지 않아야 합니다.
- 표시 목록과 이력·녹화 상한이 유지돼야 합니다. 식별 이력 합성 측정 약 0.5MiB는 참고 기준이며 전체 앱 메모리 예산이 아닙니다.
- 개선 비율/최대 전체 메모리 수치는 단계 1 실측 후 정합니다. Chrome의 영상 캐시까지 즉시 원복되는 것을 성공 조건으로 삼지 않습니다.
- 단순 코드 이동·TypeScript 컴파일 성공만으로 성능 개선을 선언하지 않습니다.

## 9. 검사와 롤백

현재 검사: `npm run typecheck`, `npm test`, `npm run test:browser`, `npm run test:chat`, `npm run test:media`. 테스트는 빌드된 dist를 로드합니다. 공통 계약은 strict TypeScript로 검사하며 기존 JS의 런타임 입력 검증을 유지합니다.

변경별로 관련 검사를 먼저 실행하고 통과 후 필요한 전체 검사를 실행합니다. 플랫폼 제한 때문에 모의 검사만으로 보장할 수 없는 확장 등록·DNR·로그인·실제 CHZZK 동작은 별도 기록합니다.

단계별 기준 커밋과 ZIP을 보존합니다. 저장 키를 유지하는 단계는 코드만 되돌릴 수 있게 하고, 데이터 스키마 변경 단계는 이전 데이터 백업·버전 판정·복원 검사를 함께 제공합니다. 문제가 생기면 해당 단계만 되돌리고 앞서 검증한 개선은 유지할 수 있게 나눕니다.
