# 메모리 최적화·리팩토링 계획

목표는 장시간 멀티뷰의 자원 사용을 측정해 줄이고, 기능별 수명과 책임을 명확하게 나누는 것입니다. TypeScript는 타입 오류 예방과 유지보수를 위해 점진 도입합니다. 이 문서는 향후 계획이며 전체 리팩토링·언어 전환을 시작한 상태는 아닙니다.

1. **기준 측정**: 같은 방송·화질로 1/4/9타일을 비교합니다. 채팅 닫힘, 원본 채팅만, 모아보기 ON, 녹화 저부하/원본, 결과 저장 Worker를 나누고 초기·10분·30분 시점의 CPU/GPU·프로세스 메모리·JS 힙을 기록합니다. Chrome 작업 관리자와 Performance/Memory 도구로 영상 버퍼와 JS 객체를 구분합니다.
2. **수명 점검**: 타일 제거·채팅 닫기·스크린샷 저장/닫기·녹화 종료·결과 창 닫기를 반복한 뒤 observer, 타이머, 이벤트 리스너, 분리된 DOM, 객체 URL, 이미지·Blob이 계속 남는지 확인합니다. 원본 플레이어의 공유 음성/영상 트랙은 종료하지 않도록 기존 격리 검사를 유지합니다.
3. **상한과 비용 정리**: 모아보기 표시 100개, 중복 식별 이력 2,048개, 방송당 녹화 256MB의 기존 상한을 검증합니다. 스크린샷 다중 캡처와 동시 녹화의 합산 메모리 제한은 측정 후 정합니다. 반복 DOM 탐색·전체 재렌더링을 줄이고 녹화/저장 모듈은 필요한 시점에만 로드합니다.
4. **모듈 분리**: viewer의 UI·상태·즐겨찾기·채팅·미디어 작업을 분리하고 프레임별 생성/해제 계약을 정합니다. 외부 메시지와 저장 데이터는 실행 시 검증을 유지합니다. 구조 정리와 새 기능 추가를 동시에 진행하지 않습니다.
5. **TypeScript 점진 도입**: 공용 데이터·메시지 규약·저장소부터 JSDoc/checkJs 또는 소규모 TS 빌드를 비교합니다. 이후 프레임 제어와 UI로 확장하고 빌드 결과·MV3 CSP·오프라인 패키지를 검사합니다.

각 단계는 기존 음량 격리·원본 채팅 조작·가상 스크롤 중복 방지·캡처/녹화 검사를 통과해야 합니다. 실제 Chrome의 장시간 사용량과 반복 해제 후 잔류 객체가 줄었는지로 성능 개선을 판정합니다. 파일 수나 언어 전환만으로 경량화됐다고 판단하지 않습니다.
